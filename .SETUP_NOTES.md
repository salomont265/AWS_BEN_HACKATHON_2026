### Issue 2: DynamoDB Permission Errors
**Problem:** All functions getting `AccessDeniedException: not authorized to perform dynamodb:PutItem`

**Root Cause:** Lambda execution roles didn't have DynamoDB permissions

**Fix Applied to users-fn:**
1. Go to Lambda → users-fn → Configuration → Permissions
2. Click the execution role name (e.g., `users-fn-role-fr8ynnut`)
3. Add permissions → Create inline policy
4. Paste this JSON:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:PutItem",
        "dynamodb:GetItem",
        "dynamodb:Query",
        "dynamodb:Scan",
        "dynamodb:UpdateItem",
        "dynamodb:DeleteItem",
        "dynamodb:BatchGetItem"
```

## Lessons Learned

1. **Always run `npm install` before zipping Lambda layers** - Empty node_modules folder won't work
2. **Check table names match code** - DynamoDB is case-sensitive
3. **ML models need HTTP servers** - Can't just run prediction scripts, need Flask/FastAPI wrapper
4. **Security groups matter** - Lambda needs port access to EC2
5. **IAM permissions are hierarchical** - User can't attach policies to roles without proper permissions
6. **Prophet models need ALL regressors** - Must provide temperature, complaint_count, etc. even for predictions
7. **GSI indexes are needed for non-key queries** - Can't query by email without email-index
8. **Private IPs don't work from Lambda (outside VPC)** - Use public IP or put Lambda in VPC

### Key Lessons Learned

**1. Lambda Proxy Integration is CRITICAL**
- Without it, Lambda doesn't get the full event (path, headers, body)
- Checkbox must be ✅ when creating method
- Symptoms: "Route not found" even though Lambda exists

**2. API Gateway Changes Require Deployment**
- Creating resources doesn't make them live
- Changing authorization doesn't take effect
- Must: Actions → Deploy API → v2 → Deploy
- Every. Single. Time.

**3. {proxy+} is Required for Sub-Paths**
- `/users` resource only handles `/users` exactly
- `/users/{proxy+}` catches `/users/anything`
- Lambda receives full path and routes internally
- Don't create `/users/{id}` - use `{proxy+}` instead

**4. Authorization Must Be NONE for JWT**
- API Gateway defaults to AWS_IAM sometimes
- Must set Method Request → Authorization → NONE
- Otherwise it tries to validate as AWS Signature v4
- Error: "Invalid key=value pair in Authorization header"

**5. Stage Name Matters**
- Deployed to `v2` stage (not `test1`)
- Stage is separate from resource paths
- Lambda sees `/users`, not `/v2/users`
- Base URL: `https://{api-id}.execute-api.{region}.amazonaws.com/{stage}`
